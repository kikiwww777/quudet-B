## 3. 各问题修复详解

### 3.1 P0：Group 状态流转

#### 问题

`_update_experiment_group_status` 的检测逻辑有遗漏：

```python
# 修复前
statuses = {r.status for r in runs}  # {"SUCCESS", "PENDING"}
if "RUNNING" in statuses:      # False — 没有任何 job 的 status 是 "RUNNING"
    new_status = "RUNNING"
elif all(s == "SUCCESS" ...):  # False — 有 PENDING
    ...
else:
    new_status = group.status  # → 保持 PENDING，永远不变！
```

#### 修复

新的检测逻辑：检查 **所有状态是否都属于终态集合**（`SUCCESS`/`FAILED`）。

```python
_TERMINAL = frozenset({"SUCCESS", "FAILED"})

all_terminal = statuses.issubset(_TERMINAL)
if all_terminal:
    # 全终态 → SUCCESS / FAILED / PARTIAL
    if all(s == "SUCCESS" for s in statuses):
        new_status = "SUCCESS"
    elif all(s == "FAILED" for s in statuses):
        new_status = "FAILED"
    else:
        new_status = "PARTIAL"
else:
    # 还有非终态（PENDING / PENDING_ASSIGN / RUNNING / RUNNING_REMOTE）
    new_status = "RUNNING"
```

#### 触发点覆盖

| 触发时机 | 文件 | 之前 | 之后 |
|---------|------|------|------|
| 本地任务完成（SUCCESS/FAILED） | executor.py | ✅ | ✅ |
| 本地任务异常退出 | executor.py | ✅ | ✅ |
| 远端节点领取任务（→RUNNING） | dispatch.py | ❌ | ✅ |
| 远端节点上报终态（SUCCESS/FAILED） | dispatch.py | ❌ | ✅ |

#### 状态机

```
PENDING
  ↓（第一个 job 开始）
RUNNING
  ↓（所有 job 终态）
  ├─ 全部 SUCCESS  → SUCCESS
  ├─ 全部 FAILED   → FAILED
  └─ 混合          → PARTIAL
```

### 3.2 P1：Compare 接口修复

#### 问题 1：字段名不匹配

compare 函数输出 dict 中用 `final_metrics` 作 key，但 `RunCompareItem` schema 期望 `metrics`。导致所有 run 的 metrics 被 Pydantic 静默丢弃。

```python
# 修复前（experiment_compare.py）
run_item = {
    ...
    "final_metrics": final_metrics,  # ← 和 schema 对不上
}

# RunCompareItem 期望：
#   metrics: dict | None
```

**修复**：统一为 `metrics`。

#### 问题 2：relative_percent 为 None 时格式化崩溃

当 baseline mean = 0 时，relative_percent 设为 None，但格式化串直接用 `:.1f` 会抛 `TypeError`。

**修复**：加 `rel is not None` 判断。

#### 问题 3：summary_text 无兜底

当全部 run 都无 metrics 时，以前只输出空行。

**修复**：全分支均有非空文案：
- `"No run data available for aggregation."`（无 runs）
- `"No successful runs with valid metrics — aggregation not possible."`（全失败或无指标）

#### 响应结构现在包含 status

```json
{
  "group_id": "xxx",
  "status": "SUCCESS",
  "primary_metric": "metrics/mAP50-95(B)",
  "runs": [...],
  "aggregates": {...},
  "delta_vs_baseline": {...},
  "best_run_id": "...",
  "summary_text": "..."
}
```

### 3.3 P2：Role 持久化

经全链路检查，role 在所有环节均已保留，无需修复：

```
ExperimentRunCreate(role="baseline")
  → json payload → schema validation → role 有默认值 "variant"
  → expand_runs() → run_info["run_role"]
  → experiments.py 创建 JobRecord(run_role=...)
  → DB 字段 job_record.run_role
  → JobRead(experiment_group_id, run_role, seed)
  → compare 函数按 r.run_role 分组
```

### 3.4 P3：兜底逻辑

| 场景 | 兜底行为 |
|------|---------|
| 所有 runs 缺 metrics | 返回空 aggregates，summary_text 明确说明 |
| compare 接口在 PENDING/PARTIAL/FAILED 状态调用 | 不依赖 group.status，直接查 runs 数据 |
| relative_percent 不可计算 | 返回 None 并标注 "N/A — baseline mean is 0" |
| 全部 run 失败 | aggregates 全部为 None，summary_text 报告 |
