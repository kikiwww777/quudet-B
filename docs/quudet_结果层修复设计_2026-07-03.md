## 0. 一句话目标

当前 `quudet` 已经可以：

- 接收 experiment group
- 展开 runs
- 真实执行 YOLO 训练
- 回收单个 run 的状态与部分产物

但还不能稳定完成：

```text
experiment group 完成状态更新
  -> compare 成功
  -> aggregates / delta_vs_baseline 返回
```

所以这次修复的核心不是“让实验能跑”，而是：

```text
让实验跑完后，结果层真正可用于下一轮实验决策。
```

---

## 1. 当前问题总结

来自最新联调结果，当前有 4 个直接影响结果层的问题。

### 1.1 实验组状态不会自动流转到完成态

现象：

- 所有 runs 都已经 `SUCCESS`
- 但 experiment group 仍停留在 `PENDING`

后果：

- `AI-Researcher` 的 `poll_group_result()` 不能可靠依赖 group status
- 只能绕过，用 run 聚合逻辑强行判完成
- `compare` 接口可能拒绝服务，因为它认为 group 还没完成

这是当前最大问题。

### 1.2 `compare` 接口返回 500

现象：

- `GET /api/v1/experiments/{group_id}/compare` 失败
- `aggregates`、`delta_vs_baseline` 为空

后果：

- Loop Brain 无法拿到最关键的结构化结果
- 下一轮实验决策质量受限
- 当前闭环虽然“能跑通”，但结果分析层仍是降级状态

### 1.3 role 信息在 runs 中丢失

现象：

- 提交时 `role=baseline / variant / ablation`
- 在 quudet 数据模型或返回结果中变成 `None`

后果：

- compare 时无法可靠按 role 分组
- baseline vs variant 聚合困难

### 1.4 当前结果层过度依赖“理想状态路径”

表现为：

- 假定 experiment group status 会自动更新
- 假定 compare 只在 group 完成后访问
- 假定 role 字段总是存在

这在联调期不稳。

## 4. P0：experiment group 状态流转修复

### 4.1 问题本质

当前 group 状态更新逻辑没有和 job/run 生命周期真正绑定。

也就是说，run 完成之后：

- 单个 job 成功
- metrics 已有
- 但 group 层没有可靠地被回写为：
  - `RUNNING`
  - `PARTIAL`
  - `SUCCESS`
  - `FAILED`

### 4.2 正确的状态机

建议明确 experiment group 状态机：

```text
PENDING
  -> RUNNING
  -> SUCCESS
  -> PARTIAL
  -> FAILED
```

#### 定义建议

- `PENDING`
  - group 已创建，尚无任何 run 开始

- `RUNNING`
  - 至少一个 run 已开始，且还有 run 未结束

- `SUCCESS`
  - 所有 runs 终态，且全部成功

- `PARTIAL`
  - 所有 runs 终态，但有成功也有失败

- `FAILED`
  - 所有 runs 终态，且全部失败

### 4.3 必须修的触发点

状态回写不能只依赖手动 compare 或轮询。  
应该在每个 run 终态写回时自动触发 group 状态更新。

重点检查文件：

- `app/tasks/executor.py`
- `app/agent/runner.py`
- `app/api/routes/experiments.py`
- `app/services/experiment_compare.py`

如果当前已有 `_update_experiment_group_status()`，优先修它，不要新造第二套。

### 4.4 建议实现逻辑

在 run 成功 / 失败的最终写库位置，统一调用：

```python
update_experiment_group_status(group_id)
```

核心逻辑：

1. 取该 group 下所有 jobs
2. 统计状态：
   - 非终态数
   - 成功数
   - 失败数
3. 按上面状态机回写 group.status

### 4.5 验收标准

给一个 4-run group：

- 4 成功 -> `SUCCESS`
- 2 成功 + 2 失败 -> `PARTIAL`
- 4 失败 -> `FAILED`
- 有 1 个还在跑 -> `RUNNING`

## 5. P1：compare 接口修复

### 5.1 当前问题本质

`compare` 接口现在很可能依赖“group 已完成”才能工作，  
但 group 状态没更新，所以 compare 直接 500。

这说明 compare 的容错性也不够。

### 5.2 修复目标

`GET /api/v1/experiments/{group_id}/compare`

必须做到：

1. 在 `SUCCESS / PARTIAL / FAILED` 三种终态下都能返回结构化结果
2. 即使部分 runs 失败，只要有可用成功结果，也能返回 aggregates
3. 不要因为某个 run 缺 metrics 就直接 500

### 5.3 compare 应返回什么

至少返回：

```json
{
  "group_id": "...",
  "status": "SUCCESS",
  "primary_metric": "metrics/mAP50-95(B)",
  "runs": [...],
  "aggregates": {
    "baseline": {"mean": ..., "std": ..., "n": ...},
    "variant": {"mean": ..., "std": ..., "n": ...}
  },
  "delta_vs_baseline": {
    "variant": {"absolute": ..., "relative_percent": ...}
  },
  "best_run_id": "...",
  "summary_text": "..."
}
```

### 5.4 容错策略

compare 不应要求“所有 run 都有完美 metrics”。

建议策略：

- 对成功且有主指标的 run 参与聚合
- 对失败 run 只进入 `runs` 列表，不参与 aggregates
- 如果 baseline 或 variant 一侧完全无可用 metrics，则显式返回空聚合并给出说明，不抛 500

### 5.5 重点检查文件

- `app/services/experiment_compare.py`
- `app/api/routes/experiments.py`

### 5.6 验收标准

#### 场景 A：全成功

- compare 返回完整 aggregates / delta

#### 场景 B：部分失败

- compare 返回可用成功 runs 的聚合
- 同时标注失败 runs
- 不 500

#### 场景 C：一侧无可用结果

- compare 返回结构化空 aggregates
- 有清晰 `summary_text`
- 不 500

## 6. P2：role 传递与持久化修复

### 6.1 问题本质

如果 `role`（baseline / variant / ablation）丢失，  
那 compare 层即使有 metrics 也无法正确做科研意义上的比较。

### 6.2 必须检查的链路

role 必须在以下全链路保留：

```text
POST /api/v1/experiments payload
  -> schema
  -> ORM model / DB field
  -> executor / runner
  -> GET detail
  -> compare aggregation
```

### 6.3 重点检查文件

- `app/schemas/experiment.py`
- `app/models/job_record.py`
- `app/api/routes/experiments.py`
- `app/services/job_expand_service.py`
- `app/services/experiment_compare.py`

### 6.4 修复要求

1. role 字段在 DB 中持久化
2. role 字段在 detail API 中返回
3. compare 层严格按 role 分组
4. 如果 role 缺失，不应静默吞掉，应显式归到 `unknown` 并记录 warning

### 6.5 验收标准

提交一个：

- baseline × 2
- variant × 2

的 experiment group 后：

- detail 中 4 个 run 都能看到正确 role
- compare 中 aggregates 至少有 `baseline` 和 `variant`

## 7. P3：结果层兜底逻辑

即使 P0/P1/P2 修完，也建议加一层兜底，避免未来再因边界情况卡住 Loop Brain。

### 7.1 group 完成态兜底

如果 group.status 仍错误，但所有 runs 已终态，  
compare 层或 adapter 层至少应能识别：

```text
all runs terminal -> treat as finished
```

当前 `AI-Researcher` 侧已经做了这个兜底，但长期应该把主逻辑修在 quudet。

### 7.2 metrics 缺失兜底

如果主指标缺失：

- 不要 500
- 返回：
  - run status
  - artifact availability
  - missing metric explanation

### 7.3 summary_text 永不为空

无论成功还是失败，compare 都应该给出：

- 当前实验组情况概述
- 哪些 role 成功
- 哪些 role 失败
- 是否足以支撑进一步比较
